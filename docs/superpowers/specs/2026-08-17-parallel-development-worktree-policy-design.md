# 并行开发与主工作树设计

## 背景

当前仓库曾让多个任务在同一个物理目录中切换分支。Git 的分支只记录已提交历史，未提交文件属于工作树而不属于分支，因此同一目录中的并行任务会共享 `HEAD`、暂存区和未提交文件。这会造成任务 A 切换分支后，任务 B 的改动出现在错误分支，甚至被误提交或误清理。

本设计建立一个稳定的本地 `main` 主工作树，并要求每个并行任务使用独立 Git worktree。项目不长期维护 `integration` 分支；只有确实需要组合验证时才临时创建。

## 目标

- `D:\product-image-workflow` 永久作为本地 `main` 主工作树。
- `main` 只接收已提交、已验证的任务分支，不直接承载日常开发。
- 每个并行任务独占一个分支和一个物理工作树。
- 未提交文件、生成输出和依赖目录不会跨任务混用。
- 默认直接将验证完成的任务分支依次合并到 `main`。
- 仅在多个分支必须组合验证时使用临时集成分支，验收后删除。

## 非目标

- 不引入长期存在的 `develop` 或 `integration` 分支。
- 不在本次设计中修改业务代码、测试代码或发布流程。
- 不自动推送远程仓库；推送仍是明确授权后的发布动作。
- 不自动删除现有脏工作树或其中的未跟踪文件。

## 分支和目录职责

| 目录 | 分支 | 职责 |
| --- | --- | --- |
| `D:\product-image-workflow` | `main` | 唯一主工作树；同步主线、合并任务、运行合并后验证 |
| `D:\product-image-workflow-<任务名>` | `codex/<任务名>` | 单一任务的设计、开发、测试和提交 |
| `D:\product-image-workflow-integration-<日期>` | `codex/integration-<日期>` | 仅在需要组合验证时临时使用 |

一个分支同一时间只能被一个工作树检出。一个任务也只能由一个工作树拥有。任务代理不得在 `D:\product-image-workflow` 中切换分支或修改文件。

## 本地主线定义

本地 `main` 是唯一开发基线，也是本地最终验收线。`origin/main` 是远程发布线。正常情况下，本地 `main` 跟踪 `origin/main`，但本地已验证提交是否推送由发布动作决定。

开始新任务前，主工作树必须满足：

1. 当前分支为 `main`。
2. `git status --short` 为空。
3. 已明确本地 `main` 与 `origin/main` 的关系。
4. 若执行远程同步，只允许快进更新；不得用强制重置覆盖本地提交。
5. 基线测试通过，或已明确记录与本任务无关的已知失败。

## 任务生命周期

### 1. 创建

任务分支从当时的本地 `main` 创建，命名为 `codex/<短任务名>`，并同时创建独立工作树。创建完成后记录绝对路径、分支名和基线提交。

### 2. 开发

所有文件修改、暂存、提交和任务测试都只发生在该任务工作树。任务不得切换其他任务的分支，也不得借用其他任务工作树。被 Git 忽略的 `outputs`、临时文件和本地配置也保留在各自工作树中。

大型且稳定的只读依赖可以显式复用，例如项目 Python 虚拟环境或 `spreadsheet_runtime\node_modules`。复用必须指向已核验的固定目录，不能把任务输出目录或可变配置作为共享目标。

### 3. 交付前验证

任务交付前至少满足：

- 任务工作树状态可解释，任务改动已全部提交。
- 运行与改动范围直接相关的测试。
- 运行完整 Python 测试套件。
- 修改前端时运行 TypeScript 检查和生产构建。
- 执行语法检查、`git diff --check` 和最终状态检查。
- 回传提交号、测试结果和 `git status --short`。

### 4. 合并

集成人只在主工作树执行合并。每次只合并一个已验证任务分支，随后立即运行主线验证。若主线验证失败，则停止后续合并并定位到刚合入的分支。

任务分支默认使用 `--no-ff` 合入 `main`，保留任务边界和来源提交。已经交给其他任务或进入评审的分支不执行变基、强推或其他历史改写。只有在创建任务时就明确约定为单提交交付，才允许在合并时压缩提交。

发生冲突时，不在含有其他未完成合并的主工作树中继续堆叠操作。先中止本次合并，再让任务分支吸收最新 `main`、解决冲突并重新测试，然后重新发起主线合并。

### 5. 清理

确认任务已进入 `main`、工作树干净且不再需要回退后，才移除任务工作树。随后删除本地任务分支。远程任务分支若存在，是否删除属于单独的远程操作。

任何含有已修改、已暂存或未跟踪文件的工作树都不得自动移除。

## 临时集成分支

默认不创建集成分支。只有同时满足以下条件时才创建：

- 两个或更多已完成分支存在跨分支行为，需要先组合验证；
- 单独测试不能证明组合后的流程正确；
- 组合验证失败时，不希望让本地 `main` 暂时承载未通过的组合。

临时集成分支必须从最新 `main` 创建。候选任务逐个合入，每次记录来源提交并运行相应测试。完整验证通过后，将临时集成结果合入 `main`；确认主线通过后删除集成工作树和分支。

临时集成分支不得成为新任务的长期基线。新任务仍从 `main` 创建，除非该任务明确依赖尚未进入 `main` 的组合结果。

## 合并后验收

每次合并到 `main` 后执行以下检查：

1. `main` 主工作树状态为空。
2. 合并提交的父提交和来源分支符合预期。
3. 完整 Python 测试套件通过。
4. 涉及前端时，前端类型检查和生产构建通过。
5. 涉及采集、生成或导出主流程时，执行对应端到端验证。
6. `git diff --check` 无空白或补丁格式错误。
7. 明确本地 `main` 相对 `origin/main` 是领先、落后还是分叉，不以目录名称代替 Git 检查。

## 故障处理原则

- 工作树出现未知改动：停止切换、合并和清理，先确认文件归属。
- 基线测试失败：记录失败并判断是依赖缺失还是代码失败；依赖修复后必须重跑。
- 合并后测试失败：停止合并后续任务，撤销方式必须保持提交可追溯，不使用破坏性重置。
- 远程主线领先：先获取远程提交并评估合并，不强推覆盖。
- 工作树目录与分支记录不一致：以 `git worktree list --porcelain` 和 `git status` 为准，不凭目录名称判断。

## 验收标准

完成本设计的后续迁移后，应满足：

- `D:\product-image-workflow` 正在检出且仅检出 `main`。
- 主工作树干净，完整测试通过。
- 所有活跃任务均有独立的 `codex/*` 分支和独立工作树。
- 不存在长期使用的 `integration` 工作树或分支。
- 脏工作树中的用户文件全部保留并有明确归属。
- 新任务可以从 `main` 创建，不会改变其他任务的 `HEAD` 或工作文件。
